# 技术方案与验证记录

> 每条按「问题 / 目标 → 方案与取舍 → 验证 → 边界」四段写。
> 所有实测均为**本机单实例**环境下的结果，度量口径在每条中注明；没有生产环境数据，也没有压测平台参与的结论。

## 1. 文章版本模型：append-only + 内容变更判定

**问题**：博客的「编辑」如果直接 UPDATE 正文，历史不可回溯；如果每次保存都插一条版本，又会产生大量无意义快照（改个错别字与重写全文等价），版本表迅速膨胀且 `current_version_id` 语义模糊。

**方案**：

- 版本表 `sd_blog_article_version` **只允许 INSERT**，不提供更新与删除；文章正文不落在主表。
- 主表用 `current_version_id` 指向当前生效版本，读取详情时由它定位正文。
- 保存时先比对内容四要素（title / summary / coverUrl / content），**只有实际变化才创建新版本**；无变化时沿用当前版本。
- 状态流转（草稿 → 发布 → 隐藏 / 下线）不改正文，因此不产生版本。
- 判定与时序规则抽成独立纯逻辑类（版本策略、状态守卫），Service 只负责编排与事务。

**验证**：纯逻辑单元测试覆盖版本创建条件、内容比对、状态守卫（`VersionPolicy` / `ArticleGuards` 两组用例，共 13 个）。测试不连数据库、不启容器。

**边界**：没有实现版本回滚 UI（数据模型支持，接口未交付）；没有做版本差异（diff）展示；`current_version_id` 的一致性靠同一事务保证，缺少数据库层的强约束（项目不使用外键）。

## 2. 全文检索：MySQL LIKE → Elasticsearch，并保留降级

**问题**：`LIKE '%词%'` 无法用索引，成本随数据量线性增长；中文没有空格分词，LIKE 只能靠碰运气命中。而且分页越过末页时框架会静默回退到第一页，深翻页语义失真。

**方案**：

- 抽出搜索服务抽象，两套实现由配置 `blog.search.engine=es|mysql` 切换，默认 ES。
- ES 侧：`multi_match`（IK 分词，标题加权），只取 id 与打分；正文回表 MySQL，按 ES 序重排，再填充标签、合并服务端高亮（命中词用 `<em>` 包裹，其余内容转义）。
- 深翻页用 `after` 游标（`search_after` 语义），规避 `from+size` 深分页代价；响应带回 `nextAfter`。
- ES 不可用时自动降级到 LIKE 实现，响应不带高亮与游标字段——**降级是功能可用性保障，不是性能保障**。

**验证**（本机单实例，2026-10-14，20040 篇合成数据 = 2 万压测样本 + 24 篇精选）：

| 场景（pageSize=10） | MySQL LIKE 中位数 | ES 中位数 | ES 命中数 |
|---|---|---|---|
| 高频词「Redis 缓存」 | 71.3 ms | 22.6 ms | 20002 |
| 高频词「MySQL 索引」 | 65.4 ms | 22.5 ms | 20004 |
| 高频词「Docker 容器」 | 64.9 ms | 21.6 ms | 20003 |
| 高频词「Spring Boot 配置」 | 64.7 ms | 20.5 ms | 20004 |
| 高频词「微服务 网关」 | 66.6 ms | 21.3 ms | 20001 |
| 低频词「Python爬虫」 | 67.3 ms | 17.6 ms | 2 |
| 空结果词「量子纠缠」 | 65.3 ms | 5.7 ms | 0 |

- **口径**：`curl -w time_total` 端到端（含网络、序列化、Java 回表与高亮），每组连打 10~11 次取中位数并剔除首次冷启动；两个引擎分别重启后端后各跑一轮。数据量级 2 万篇。
- **可读出的结论**：LIKE 的成本与命中数无关（0 命中也 65ms，即全表扫描），ES 全组 5.7~22.6ms；差距约 3 倍，且这是 2 万行的地板值。
- 中文分词另有一组定向验证：「Python爬虫」能命中「Python 爬虫入门」，自定义词典里的技术词整词命中。

**边界**：单机单实例、合成数据、无并发加载，**不能当生产压测引用**；ES 原生耗时（剥离回表成本）未逐一填表；没有做数据量梯度（10 万 / 100 万）与硬件对比。

## 3. 搜索侧的可见性红线：三条件内建于索引生命周期

**问题**：搜索引擎是第二份数据副本，最容易出的问题是「库里已隐藏、索引里还能搜到」。尤其管理员下线与作者自我隐藏是两个独立状态位，任何一个漏判都会造成越权读取。

**方案**：

- 索引只装公共可见文章：判定条件为 `已发布 AND 公共 AND 未删除`，在**写索引时**统一推导，8 个写方法（发布、编辑、隐藏、恢复、下线、删除等）都通过同一事件出口触发。
- **读路径再过滤一次**：ES 只返回 id，正文回表时的 SQL 内建同一组条件；即使索引里残留脏文档，也查不出数据。
- 事件监听放在事务提交之后，避免「事务回滚了但索引已更新」。
- 定时对账：比对 MySQL 公共文章集合与 ES 文档集合的差集，双向修正；事件失败只记日志，由对账兜底。
- 重建走「新索引 → reindex → 单请求原子切换 alias」，切换期间读旧索引。

**验证**：

- 越权类用例：草稿 / 作者隐藏 / 管理员下线 / 逻辑删除四类文章均不出现在搜索结果中（Apifox 用例，人工执行）。
- 索引重建：20040 篇 reindex 用时 2336ms，随后单请求原子切换 alias，全程并发搜索 **55/55 全 200**（实测记录，不是压测）。
- 对账：直接改库把一篇文章改成不可见但不发事件，对账任务能发现并修正该差异。
- 编辑内容后索引同步更新（title / summary / content 三处变化均触发）。

**边界**：「切换零中断」只适用于上述 alias 原子切换场景，不能扩展到发布、部署或数据库迁移；对账是定时任务，存在最长一个周期的不一致窗口。

## 4. 阅读量：Redis 增量 + 去重 + 降级

**问题**：详情页每次刷新都 `UPDATE view_count + 1` 会把写压力全部压到主库，热点文章尤其明显；但阅读量又必须可读、不能丢。

**方案**：

- 计数点收敛在**详情接口一处**，其它接口不参与计数。
- Redis 记增量与访客标识（登录用户按 userId，匿名按访客指纹），**同一访客 30 分钟内只 +1**；读取时返回 DB 值 + 待落库增量，列表页只读 DB。Redis 开启 AOF，尽量降低重启丢增量。
- 定时把增量合并写回 DB；**DB 是唯一真相源**，增量丢失只会少计，不会出现负值或回退。
- Redis 故障时降级直写 DB，详情接口仍返回 200。

**验证**：人工实测（2026-10-14）：连续刷新同访客只 +1；换浏览器 +1；登录态按用户去重正常；flush 后 DB 追平页面显示；停掉 Redis 期间详情持续 200 并按降级路径直写 DB。

**边界**：验证为**串行人工操作**，不是并发一致性验证；「杀进程重启不丢增量」依赖 AOF，未在重启场景复测；没有做热点文章的并发压测。

## 5. 安全与治理的几条实现约束

**问题**：内容平台的风险集中在「谁能改谁的文章」与「用户提交的 HTML 能不能直接信」。

**方案**：

- **归属校验在后端**：作者的增删改查全部按当前登录用户过滤，前端传的 `authorId` 不参与鉴权；隐藏/删除自己的文章与管理员下线的状态位相互独立。
- **富文本入库前净化**：危险标签、事件属性、危险 URL 协议在保存时处理，正文以「净化后 HTML 快照」存储。
- **接口限流**：按接口点位区分限流键，超限返回统一错误；限流键生成与判定是可独立测试的纯逻辑。
- **标签合并**：重命名产生旧 slug → canonical 的 alias；合并需要展平别名链、迁移文章关系、去重，避免「别名指向别名」的链式解析与重复标签。
- **编辑器与渲染分离**：作者端的富文本编辑器只在浏览器端加载（不进服务端渲染），读者端只渲染已净化的 HTML 并做排版。

**验证**：净化、限流键、限流检查、标签合并在单元测试中覆盖（共 22 个用例）；越权与鉴权失败通过接口用例人工验证；限流做了三点位超限的人工实测（超限被拒、未超限无感、Redis 键核验）。

**边界**：净化基于标签与属性的黑名单策略，不做完整的 HTML 语义校验；限流是单实例 Redis 计数，不涉及多节点全局限流；没有第三方安全评估或渗透测试。

## 6. 发布链：镜像不可变 + 部署机不编译

**问题**：一键 Compose 能起栈，但 compose 里带 `build:`、没有镜像推送与回滚路径，发布时要么在目标机编译，要么带着源码跑，回滚只能靠手改 tag。

**方案**：

- 三个仓库各自 CI 门禁（后端 `clean verify`、两个前端 install + build + test/lint）；打 tag 时各仓产不可变镜像：后端、ES（自建 IK 镜像）、管理后台、读者站。
- 发布工作流单独入口，先**预检四个镜像齐备**再往下走；部署机只 `pull` 镜像，不 clone 源码、不编译、不持构建缓存。
- 部署脚本封装：起栈、切换版本、回滚、备份、恢复、状态查询；按 digest 记录「当前/上一组」，回滚按 digest 而不是 tag。
- 部署包携带有序 SQL 与中间件配置，空目录可直接初始化；栈内与公网各有冒烟脚本。
- 与另一个项目共用一台宿主机：镜像清理按项目前缀，部署加文件锁互斥。

**验证**（2026-10-30，本机演示栈）：

- 空目录起栈：初始化 31 张表 / 7 张博客表 / 15 条菜单，无错误。
- 栈内冒烟 19/19；公网冒烟 8/8（两个入口 + 反代 + sitemap + 图片链路）。
- `up → rollback → 前滚` 三连各 19/19 通过，状态文件正确记录四枚 digest。
- 备份 → 删库 → 恢复：五项行数一致（52 篇 / 52 版本 / 200 评论 / 20 标签 / 8 用户），搜索与图片恢复可用。
- 发布工作流全流程（预检 + 解包 + 起栈 + 公网冒烟）实测全绿。

**边界**：这是**单机演示环境的发布链**，没有云主机、没有多环境（staging）、没有灰度或蓝绿、没有 K8s；数据库无迁移框架，回滚只回镜像，schema 变更需显式标记并人工前滚；备份与数据同盘，不防磁盘损坏。
